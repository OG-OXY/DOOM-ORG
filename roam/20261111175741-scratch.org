#+begin_src nix
{ config, pkgs, ... }:

{
  programs.mpv = {
    enable = true;
    
    # 1. High-Quality Rendering & Video/Image Settings
    config = {
      # Use the high-quality profile base
      profile = "high-quality";
      # Force use of a high-performance GPU context (Vulkan preferred, fallback to OpenGL)
      gpu-api = "vulkan";
      vo = "gpu-next";
      
      # Advanced Quality Upscaling
      scale = "ewa_lanczossharp"; # High-end Jinc/Lanczos scaling for extreme clarity
      cscale = "lanczos";         # Chroma upscaling
      dscale = "mitchell";        # Downscaling algorithm
      correct-downscaling = "yes";
      linear-downscaling = "yes";
      sigmoid-upscaling = "yes";
      
      # Performance & Behavior
      hwdec = "auto-safe";        # Hardware decoding for videos in your folders
      keep-open = "yes";          # Don't close the window when an image/video ends
      reset-on-next-file = "video-aspect-override,loop-file,speed,sub-delay,video-pan-x,video-pan-y,video-zoom"; # Reset zoom level when flipping to next image
      
      # Fix image behavior (force mpv to recognize images instead of treating them as 1-second audio)
      image-display-duration = "inf"; 
      loop-file = "inf";
    };

    # 2. Keybindings tailored for image browsing
    bindings = {
      # Navigation (Arrow keys or Mouse Wheel)
      "RIGHT" = "playlist-next";
      "LEFT" = "playlist-prev";
      "SPACE" = "playlist-next";
      "BS" = "playlist-prev"; # Backspace to go back
      "WHEEL_UP" = "playlist-prev";
      "WHEEL_DOWN" = "playlist-next";

      # Zooming and Panning (Holding Alt + Arrow Keys or +/-)
      "=" = "add video-zoom 0.1";
      "-" = "add video-zoom -0.1";
      "Alt+left" = "add video-pan-x 0.05";
      "Alt+right" = "add video-pan-x -0.05";
      "Alt+up" = "add video-pan-y 0.05";
      "Alt+down" = "add video-pan-y -0.05";
      "Ctrl+0" = "set video-zoom 0; set video-pan-x 0; set video-pan-y 0"; # Reset zoom
    };

    # 3. Scripts that make mpv behave like an image app
    scripts = with pkgs.mpvScripts; [
      # Crucial: Automatically grabs all other images/videos in the directory 
      # so you don't have to open them one by one.
      mpris 
      autoload 
    ];
  };

  # Optional: Create a quick terminal alias 'mvi' so you don't confuse it with normal video playback
  home.shellAliases = {
    mvi = "mpv --image-display-duration=inf";
  };
}

** Does Order Matter, Emacs Configurations, Use-Package
:PROPERTIES:
:CUSTOM_ID: does-order-matter-emacs-configurations-use-package
:END:
In =use-package=, the keywords (=:demand=, =:custom=, =:bind=,
=:config=, =:hook=, =:init=, etc.) *can generally be placed in any
order*.

=use-package= is a macro, meaning it parses all of those keyword blocks
and reorganizes them into a standard, correct Elisp structure behind the
scenes before Emacs executes the code.

However, while keyword order rarely breaks syntax, *there are two
specific exceptions where order strictly matters*.

--------------

*** Exception 1: Macro Variable Declarations (=:defines= & =:functions=)
:PROPERTIES:
:CUSTOM_ID: exception-1-macro-variable-declarations-defines-functions
:END:
If you use =:defines= or =:functions= to quiet byte-compiler warnings,
they *must appear before* the code that references those variables or
functions (such as inside =:init= or =:config=).

#+begin_src elisp
;; GOOD: :defines comes before :init accesses the variable
(use-package my-pkg
  :defines my-pkg-variable
  :init
  (setq my-pkg-variable t))
#+end_src

--------------

*** Exception 2: Multiple Instances of the Same Keyword
:PROPERTIES:
:CUSTOM_ID: exception-2-multiple-instances-of-the-same-keyword
:END:
If you use the same keyword more than once in a single =use-package=
block, =use-package= evaluates or applies them *in the order they are
written from top to bottom*.

#+begin_src elisp
;; Order matters here! theme-b will run second and overwrite theme-a
(use-package doom-themes
  :config
  (load-theme 'doom-one t)
  :config
  (load-theme 'doom-nord t))
#+end_src

--------------

*** Recommended Standard Layout (Best Practice)
:PROPERTIES:
:CUSTOM_ID: recommended-standard-layout-best-practice
:END:
Even though =use-package= reorganizes keywords under the hood, adopting
a consistent lifecycle order keeps your =.el= files readable and
maintainable.

Here is the standard community convention:

#+begin_src elisp
(use-package package-name
  :demand t               ; 1. Load behavior (:demand, :defer)
  :init                   ; 2. Code to run BEFORE the package loads
  (setq variable-a t)

  :custom                 ; 3. Package user options / customization
  (package-option t)

  :bind                   ; 4. Keybindings & Hooks (Triggers)
  ("C-c a" . my-command)
  :hook
  (prog-mode . my-mode)

  :config                 ; 5. Code to run AFTER the package loads
  (package-setup-function))
#+end_src

:PROPERTIES:
:CUSTOM_ID: summary
:END:
- *Can you mix up the keywords?* Yes. Writing =:config= before =:custom=
  or =:demand= after =:bind= will work fine because the macro
  restructures it during compilation.
- *Is there a performance difference?* No. Keyword order in
  =use-package= has zero effect on runtime performance or the Emacs
  daemon.

** How Do I Defer Emacs Packages
:PROPERTIES:
:CUSTOM_ID: how-do-i-defer-emacs-packages
:END:
In =use-package=, adding a *=:bind=* block automatically defers the
package by default. Emacs creates light autoload stubs for the bound
commands (=org-roam-node-find=, etc.) and completely skips loading
=org-roam.el= until you press one of those key combinations.

However, because you have *=(org-roam-setup)=* inside =:config=, there
is one important detail to watch out for: *=org-roam-setup= turns on
background hooks* (like database syncing and file modification
listeners).

--------------

**** Option 1: Defer on Keybinds (Standard Lazy Loading)
:PROPERTIES:
:CUSTOM_ID: option-1-defer-on-keybinds-standard-lazy-loading
:END:
If you only want =org-roam= to load and initialize when you actually
trigger one of your Org-Roam keybindings, leave it as you wrote it.
=use-package= handles the deferral automatically:

#+begin_src elisp
(use-package org-roam
  :custom
  (org-roam-directory (expand-file-name "Roam" org-directory))
  :bind (("C-c n l" . org-roam-buffer-toggle)
         ("C-c n f" . org-roam-node-find)
         ("C-c n i" . org-roam-node-insert))
  :config
  ;; This will ONLY run the first time you press C-c n l, C-c n f, or C-c n i
  (org-roam-setup))
#+end_src

- *How it behaves:* =org-roam.el= stays completely unparsed in memory
  until you hit =C-c n f= (or your leader equivalent). Upon keypress,
  Emacs loads the package, runs =(org-roam-setup)= to initialize the DB
  connections, and opens the node finder interface.

--------------

**** Option 2: Defer Loading Until You Open an Org File (=:hook=)
:PROPERTIES:
:CUSTOM_ID: option-2-defer-loading-until-you-open-an-org-file-hook
:END:
If you want =org-roam= to be ready as soon as you start working in
Org-mode (so database syncing and auto-completion work immediately, but
without slowing down non-Org editing or daemon boot), defer it with a
hook instead:

#+begin_src elisp
(use-package org-roam
  :custom
  (org-roam-directory (expand-file-name "Roam" org-directory))
  :hook (org-mode . org-roam-setup)
  :bind (("C-c n l" . org-roam-buffer-toggle)
         ("C-c n f" . org-roam-node-find)
         ("C-c n i" . org-roam-node-insert)))
#+end_src

--------------

**** Option 3: Eagerly Load on Daemon Boot (=:demand t=)
:PROPERTIES:
:CUSTOM_ID: option-3-eagerly-load-on-daemon-boot-demand-t
:END:
Since you run an Emacs daemon and prefer *zero cold-start latency* when
searching your notes, pre-loading =org-roam= at daemon startup prevents
a 100ms SQLite database initialization delay on your first =C-c n f=
press:

#+begin_src elisp
(use-package org-roam
  :demand t ; Pre-warms the SQLite database in background daemon RAM
  :custom
  (org-roam-directory (expand-file-name "Roam" org-directory))
  :bind (("C-c n l" . org-roam-buffer-toggle)
         ("C-c n f" . org-roam-node-find)
         ("C-c n i" . org-roam-node-insert))
  :config
  (org-roam-setup))
#+end_src

:PROPERTIES:
:CUSTOM_ID: key-takeaway
:END:
- Writing **=:bind= automatically implies =:defer t**=---you do not need
  to explicitly write =:defer t=.
- For a daemon setup, *Option 1* keeps it deferred until invoked, while

** Demand t Is Never Redundant
:PROPERTIES:
:CUSTOM_ID: demand-t-is-never-redundant
:END:
/Spot on. You nailed the logic./

=use-package= automatically assumes a package should be deferred if you
give it certain triggers like =:bind=, =:hook=, =:commands=, or =:mode=.
Writing =:defer t= explicitly alongside those triggers is completely
redundant.

**** How =use-package= Decides to Defer
:PROPERTIES:
:CUSTOM_ID: how-use-package-decides-to-defer
:END:
- /Implicitly Deferred (No extra flags needed):/ If you use =:bind=,
  =:hook=, =:commands=, or =:mode=, =use-package= automatically turns on
  lazy-loading behind the scenes. It sets up autoloads so the package
  stays unloaded until you hit the key or trigger the hook.
- /Explicitly Eager (=:demand t=):/ Because triggers like =:bind= or
  =:hook= force lazy-loading by default, =:demand t= acts as the
  override switch. It tells =use-package=: /"Ignore the fact that I
  bound a key or hooked this---load and evaluate this package
  immediately right now."/

**** Summary Rule of Thumb
:PROPERTIES:
:CUSTOM_ID: summary-rule-of-thumb
:END:
- /Using =:bind= or =:hook=?/ Just write the bind or hook. Leave
  =:defer t= out.
- /Want it pre-warmed in the daemon right away?/ Drop in =:demand t= and
  it overrides any built-in deferral behavior.

:PROPERTIES:
:CUSTOM_ID: writing-the-function-and-the-result
:END:
To reduce boilerplate to absolute zero, we can write a helper function
that /automatically extracts parent directories/ so you never have to
manually write a =d= line again. It can accept a type (=L+= for strict
symlinks, =C+= for mutable copies), handle multiple users (=ty= and
=root=) automatically, and be injected globally via a custom system
module.

Here is how you build and wire the =systemdLinksModule= to handle this
across your entire flake.

*** The Helper Module (=systemdLinksModule.nix=)
:PROPERTIES:
:CUSTOM_ID: the-helper-module-systemdlinksmodule.nix
:END:
Create a shared module in your repo that defines =mkLinks= and injects
it into module arguments or makes it globally available:

#+begin_src nix
{ lib, config, ... }:

let
  users = [
    { name = "ty"; home = "/home/ty"; group = "users"; }
    { name = "root"; home = "/root"; group = "root"; }
  ];

  # The core helper engine
  # Takes a list of specs: [ { path = ".config/helix/config.toml"; source = helixConfig; type = "L+"; } ]
  mkLinks = entries:
    let
      expandEntry = u: entry:
        let
          fullPath = "${u.home}/${entry.path}";
          # Automatically parse the parent directory from the target path!
          dirPath = builtins.dirOf fullPath;
          ruleType = entry.type or "L+"; # Defaults to symlink (L+), can be overridden to (C+)
        in [
          "d ${dirPath} 0755 ${u.name} ${u.group} -"
          "${ruleType} ${fullPath} - - - - ${entry.source}"
        ];
    in
    lib.unique (lib.flatten (map (u: map (e: expandEntry u e) entries) users));

in
{
  # Option 1: Expose mkLinks globally via specialArgs or a custom module attribute
  # Option 2: Provide it directly to any module that imports this or uses config.lib
  config.systemd.tmpfiles.rules = mkLinks (config.systemd.userLinks or []);

  # Define a custom option so any module can cleanly declare its links
  options.systemd.userLinks = lib.mkOption {
    type = lib.types.listOf (lib.types.submodule {
      options = {
        path = lib.mkOption { type = lib.types.str; };
        source = lib.mkOption { type = lib.types.path; };
        type = lib.mkOption { type = lib.types.enum [ "L+" "C+" ]; default = "L+"; };
      };
    });
    default = [];
  };
}

***** Waypipe VS Standard SSH
:PROPERTIES:
:CUSTOM_ID: waypipe-vs-standard-ssh
:END:

  drawing commands of a /single/ GUI application on your host PC,
  compresses them, tunnels them over your encrypted SSH/Tailscale
  connection, and renders them into a local Wayland viewer running on
  your phone.

/Verification:/ The application window should spawn through the SSH link
and map back to your local client display.

** Eager vs. Lazy Loading
:PROPERTIES:
:CUSTOM_ID: eager-vs.-lazy-loading
:END:
*** What "Eager Loading at Startup" Means
:PROPERTIES:
:CUSTOM_ID: what-eager-loading-at-startup-means
:END:
/Eager loading/ (or loading unconditionally at startup) means that the
moment Emacs boots up and reads your =init.el=, it immediately compiles,
evaluates, and loads the entire package's code into active memory.

- /The Cost:/ Every package you eagerly load adds to your Emacs
  cold-start boot time. If you eagerly load 50 heavy packages, your
  startup time crawls.
- /The Benefit:/ It is guaranteed to be ready. There is zero delay or
  "autoload stub" overhead the first time you try to use it. /(Note: If
  you run Emacs as a background daemon for your Ghostty/herdr splits,
  cold-start boot time matters less day-to-day, but keeping it lean is
  still best practice)./

--------------

*** How to Decide Eager vs. Lazy Loading
:PROPERTIES:
:CUSTOM_ID: how-to-decide-eager-vs.-lazy-loading
:END:
You make the decision based on *when* the package needs to be active in
order for your workflow not to break.

**** 1. Eager Load (=:demand t=) --- Use Sparingly
:PROPERTIES:
:CUSTOM_ID: eager-load-demand-t-use-sparingly
:END:
You eager-load a package *only* if it meets one of these strict
criteria:

- /Global Minor Modes:/ It fundamentally alters how every single buffer
  behaves globally from the second you open a window (e.g.,
  =helix-mode=, global line numbers, global completion backends).
- /Themes & UI Layouts:/ Visual frameworks that need to paint the screen
  immediately so you don't get a flash of unstyled white/default text on
  startup (e.g., =doom-one=, your dashboard).

**** 2. Lazy Load (=:bind=, =:hook=, =:commands=, =:mode=) --- Default to This
:PROPERTIES:
:CUSTOM_ID: lazy-load-bind-hook-commands-mode-default-to-this
:END:
You lazy-load everything else. =use-package= makes this automatic by
creating lightweight placeholders. The package code stays unloaded until
a specific trigger occurs:

- /Keybindings (=:bind=):/ Magit doesn't load into memory until you hit
  =C-x g=.
- /Hooks (=:hook=):/ =org-modern= or =org-appear= don't load until you
  actually open an =.org= file and enter =org-mode=.
- /File Extensions (=:mode=):/ Markdown or Python linters don't load
  until you open a file ending in =.md= or =.py=.

--------------

*** How This Applies to Your =init.el=
:PROPERTIES:
:CUSTOM_ID: how-this-applies-to-your-init.el
:END:
Looking at your clean configuration architecture, here is how your
packages naturally divide:

- /Eager Loaded (=:demand t= or global init):/

- =helix-mode= (Needs to hook into every buffer instantly).

- =vertico= / =corfu= (Global completion engine).

- Theme & UI toggles.

- /Lazy Loaded (Deferred via hooks/binds):/

- =magit= (Loads only on =C-x g=).

- =org-roam= / =org-modern= (Loads only when entering =org-mode=).

- =pandoc-mode= (Loads only when markdown/org files trigger the hook).

** Emacs Lazy Loading
:PROPERTIES:
:CUSTOM_ID: emacs-lazy-loading
:END:
Hell no, lazy loading isn't exclusive to Doom at all! Doom just wraps
standard Emacs primitives---primarily *=use-package=*-behind its own
heavy macro-abstractions.

The best part? Since you're running Emacs 31 (=emacs-pgtk-31.1=),
=use-package= is built right into GNU Emacs core. You don't even need to
pull in an external library for it; it's native.

Instead of writing raw =require= statements that load everything
upfront, you use =use-package= keywords to defer loading until a command
is actually run, a hook fires, a key is pressed, or a file type is
opened.

*** How Lazy Loading Works in Vanilla Emacs
:PROPERTIES:
:CUSTOM_ID: how-lazy-loading-works-in-vanilla-emacs
:END:
You get the exact same granular deferred loading that Doom uses, but
with full transparency:

#+begin_src elisp
;;; init.el -*- lexical-binding: t; -*-

;; 1. Built-in use-package configuration
(require 'use-package)
(setq use-package-always-ensure nil) ; Since Nix manages packages, don't let MELPA auto-install

;; 2. Lazy load Evil only when entering modal states (or globally if you want it instantly)
(use-package evil
  :init
  (setq evil-want-keybinding nil)
  :config
  (evil-mode 1))

;; 3. Lazy load Magit ONLY when you run `M-x magit-status`
(use-package magit
  :commands (magit-status magit-dispatch))

;; 4. Lazy load Majutsu only when you invoke its workflow commands
(use-package majutsu
  :after magit
  :commands (majutsu-status))

;; 5. Lazy load your Helix Emulation Layer (hel) on global hook or keybinding
(use-package hel
  :after evil
  :hook (after-init . global-hel-mode))
#+end_src

*** The Key Deferral Keywords
:PROPERTIES:
:CUSTOM_ID: the-key-deferral-keywords
:END:
- /=:commands (cmd1 cmd2)=/ --- Doesn't load the package until you
  explicitly run one of those commands.
- /=:bind ("C-c x" . some-func)=/ --- Doesn't load the package until you
  hit that specific keybinding.
- /=:hook (some-mode . some-func)=/ --- Waits to load until that
  specific major/minor mode hooks in.
- /=:defer t=/ --- Defers loading until idle time or explicit reference.

You aren't locked into Doom's ecosystem to get a snappy startup time;
Vanilla Emacs with proper =use-package= triggers will snap open
instantly without bloating your memory.

** Overrides for Emacs's =H-E-L=
:PROPERTIES:
:CUSTOM_ID: overrides-for-emacss-h-e-l
:END:
In Helix (and Kakoune), /a 1-character selection IS the normal cursor
state/. There is no such thing as a cursor floating in the void
"between" characters without highlighting what it's on. When you jump
around, that single highlighted box gives you instant, unmistakable
spatial feedback: /if I press =d= or =c= right now, THIS exact character
dies./

When =hel= strips that away, forces a thin bar cursor, and defaults to
deleting /backward/ without a visual region, it throws out the core
promise of object-action editing. You're left guessing where the point
boundary actually sits.

--------------

*** The Clean Overrides to Reclaim Your Helix Experience
:PROPERTIES:
:CUSTOM_ID: the-clean-overrides-to-reclaim-your-helix-experience
:END:
Since we know /why/ =hel= was behaving so weirdly, we can completely
override the maintainer's opinions in your =init.el=.

Here is the targeted snippet to drop into your Vanilla =init.el= under
the =(use-package hel)= block. It reinstates the high-visibility /block
cursor/, forces =d= to delete forward (or delete the active selection),
and fixes =gl=/=gh= so they act like simple, non-selecting goto motions:

#+begin_src elisp
;; --- 3. Helix Emulation Layer (hel) ---
(use-package hel
  :config
  ;; 1. OVERRIDE AUTHOR CURSOR DEFAULTS: Bring back high-visibility block cursor in Normal state!
  (setq hel-normal-cursor 'box       ; Solid block cursor so you always see the 1-character selection
        hel-insert-cursor 'hbar)     ; Underline (or 'bar) for Insert state so your eyes don't lose it

  ;; 2. Activate hel safely
  (if (fboundp 'hel-global-mode)
      (hel-global-mode 1)
    (global-hel-mode 1)))

;; Fix keybindings & motion math after hel loads
(with-eval-after-load 'hel
  ;; FIX 'd': Delete active selection, OR delete character forward under the block cursor
  (defun my/hel-delete-inclusive ()
    "Delete active region if present, otherwise delete character directly under the block cursor."
    (interactive)
    (if (use-region-p)
        (call-interactively #'hel-delete)
      (delete-char 1)))

  (define-key hel-normal-mode-map (kbd "d") #'my/hel-delete-inclusive)

  ;; FIX 'gl' and 'gh': Jump to line start/end WITHOUT forcing persistent regional selections
  (defun my/hel-goto-line-end ()
    (interactive)
    (deactivate-mark)
    (move-end-of-line 1))

  (defun my/hel-goto-line-start ()
    (interactive)
    (deactivate-mark)
    (move-beginning-of-line 1))

  (when (boundp 'hel-goto-map)
    (define-key hel-goto-map (kbd "l") #'my/hel-goto-line-end)
    (define-key hel-goto-map (kbd "h") #'my/hel-goto-line-start)))
#+end_src

*** 2. Terminal: =refine-scratch= Fish Function
:PROPERTIES:
:CUSTOM_ID: terminal-refine-scratch-fish-function
:END:
If you want to automate the batch conversion straight from your command
line without opening Emacs first, you can use a clean Fish function.

Create =~/.config/fish/functions/refine-scratch.fish=:

#+begin_src fish
function refine-scratch --description "Auto-split markdown scratch headings into
atomic Org nodes"
    set -l input_file $argv[1]
    set -l target_dir ~/Org/Nodes # Adjust to your actual Org nodes directory path

    if not test -f "$input_file"
        echo "Error: File '$input_file' not found."
        return 1
    end

    # Ensure target directory exists
    mkdir -p $target_dir

    # First, convert markdown to temporary org buffer via pandoc
    set -l temp_org (mktemp --suffix=.org)
    pandoc -f markdown -t org "$input_file" -o $temp_org

    # Process headings and extract into separate .org files
    awk -v out_dir="$target_dir" -v date_str=(date +%Y-%m-%d) '
    BEGIN { current_file = ""; }
    /^(\*|\*\*|\*\*\*) / {
        # Clean up heading title for filename
        raw_title = $0;
        sub(/^(\*|\*\*|\*\*\*) /, "", raw_title);
        
        filename = tolower(raw_title);
        gsub(/[^a-z0-9_-]/, "_", filename);
        gsub(/_+/, "_", filename);
        sub(/^_/, "", filename);
        sub(/_$/, "", filename);
        
        if (filename == "") next;

        current_file = out_dir "/" date_str "_" filename ".org";

        # Write Org Frontmatter
        print "#+title: " raw_title > current_file;
        print "#+date: " date_str >> current_file;
        print "#+filetags: :inbox:\n" >> current_file;
        next;
    }
    {
        if (current_file != "") {
            print $0 >> current_file;
        }
    }
    ' $temp_org

    # Clean up temp file
    rm $temp_org

    echo "Successfully split '$input_file' into atomic Org nodes in '$target_dir'."
end
#+end_src

:PROPERTIES:
:CUSTOM_ID: workflow-in-terminal

3. Once processed, you can delete or archive the scratch file and open a

That strategy is bulletproof. Separating /capture/ (raw, frictionless

*** Org-mode Core Features (The Structure Layer)
:PROPERTIES:
:CUSTOM_ID: org-mode-core-features-the-structure-layer
:END:
Org-mode isn't just text; it's a structured tree format with properties,
execution capabilities, and metadata attached to every node.

**** Document Metadata & Headlines
:PROPERTIES:
:CUSTOM_ID: document-metadata-headlines
:END:
Every Org file and headline can act as an independent data node.

- /Headlines (=*=, =**=, =***=):/ Define hierarchical folding nodes.
- /Keywords (=TODO=, =DONE=, =RESEARCH=, =HOLD=):/ Native state tracking
  for action items embedded right inside your documentation.
- /Tags (=:rust:std:memory:=):/ Fast, non-hierarchical categorization.
  Tags inherit down headline trees.

**** Property Drawers (=:PROPERTIES:=)
:PROPERTIES:
:CUSTOM_ID: property-drawers-properties
:END:
Property drawers are hidden key-value stores attached to any specific
headline or file. This is where Org transforms from flat text into a
/queryable database/.

#+begin_src org
,* Option<T> & Result<T> Enum Memory Layout
:PROPERTIES:
:ID:       eb7a23c4-8f12-4c22-b919-94bf8c3da872
:CATEGORY: rust-std
:TYPE:     type-layout
:COMPILER_VERSION: 1.82.0
:SOURCE:   https://doc.rust-lang.org/std/option/
:END:
#+end_src

- /Why it matters:/ You can use tools like Org-Agenda or custom Elisp
  script functions to query your vault for specific properties (e.g.,
  "Find all notes where =:TYPE:= is =type-layout= and =:CATEGORY:= is
  =rust-std=").

**** Literate Programming & Babel Code Blocks (=#+BEGIN_SRC=)
:PROPERTIES:
:CUSTOM_ID: literate-programming-babel-code-blocks-begin_src
:END:
In Org-mode, code blocks aren't just for syntax highlighting---they can
be executed directly inside the buffer using /Org-Babel/.

#+begin_src org
,#+BEGIN_SRC rust :exec cargo run :results output
fn main() {
    println!("Size of Option<u8>: {} bytes", std::mem::size_of::<Option<u8>>());
    println!("Size of Option<NonZeroU8>: {} bytes", std::mem::size_of::<Option<std::num::NonZeroU8>>());
}
,#+END_SRC
#+end_src

- /Why it matters:/ As you research the Rust standard library, you can
  write micro-benchmarks or pointer-checking snippets directly inside
  your research notes, hit =C-c, C-c=, run =cargo= behind the scenes, and
  print the output directly below the code block.

*** Org-Roam Features (The Graph & Linkage Layer)
:PROPERTIES:
:CUSTOM_ID: org-roam-features-the-graph-linkage-layer
:END:
Org-roam sits on top of Org-mode and manages an automated /SQLite
database/ indexing all your files, headlines, links, and property
drawers in real time.

**** Node Creation (=org-roam-node-find= / =org-roam-node-insert=)
:PROPERTIES:
:CUSTOM_ID: node-creation-org-roam-node-find-org-roam-node-insert
:END:
- /File Nodes:/ An entire =.org= file representing one overarching topic
  (e.g., =20261026054900-rust_std_allocator.org=).
- /Headline Nodes:/ Any headline with an =:ID:= property drawer
  automatically becomes an independent node in the Org-roam database
  without needing its own separate file.

**** Aliases & Roam Tags
:PROPERTIES:
:CUSTOM_ID: aliases-roam-tags
:END:
- /Aliases (=#+ROAM_ALIASES:= or =:ROAM_ALIASES:=):/ Assign multiple
  names to a single concept node so you can link to it naturally under
  different terms.

- /Example:/ A node titled =Ownership & Borrowing= can have aliases
  ="Borrow Checker"=, ="Lifetimes"=, and ="Move Semantics"=. Inserting a
  link to any of those terms links to the exact same core node.

- /Roam Tags (=#+FILETAGS:=):/ High-level categorization used by
  Org-roam to filter search completion buffers (e.g.,
  =#+FILETAGS: :rust:concept:=).

**** Direct Links vs Back-links (Graph Dynamics)
:PROPERTIES:
:CUSTOM_ID: direct-links-vs.-backlinks-graph-dynamics
:END:
- /Direct Links (=id:...=):/ Point from the current note directly to a
  specific target node or headline.
- /Backlinks:/ Org-roam automatically tracks every node that links /to/
  the node you are currently viewing. You never have to manually
  construct cross references when you open a note on =std::pin::Pin=,
  the Org-roam sidebuffer shows every other note in your system that
  references =Pin=.
